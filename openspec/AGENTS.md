# OpenSpec Playbook

Read this file before touching any spec.

## Directory layout

```text
openspec/
├── specs/<capability>/spec.md
├── changes/<change-id>/
│   ├── proposal.md
│   └── specs/<capability>/spec.md
└── changes/archive/YYYY-MM-DD-<id>/
```

The execution plan lives in `docs/plans/`, generated by `ss-plan`.

## Workflow entry points

| Goal | Skill |
|------|-------|
| Plan a requirement and generate a delta | `ss-plan` |
| Look up capabilities | `ss-show-spec` |
| List active changes | `ss-list-changes` |
| Trace requirement history | `ss-trace-spec` |
| Merge a delta into the source of truth | `ss-archive` |
| Run a requirement end to end | `ss-feature-workflow` |

## Hard rules

Before changing behavior:

1. List the affected capabilities.
2. Read each affected current spec.
3. State whether the change is compatible, breaking, or a replacement.

Do not hand-edit `specs/<capability>/spec.md`; use `ss-archive`.

Every delta requirement must contain at least one `#### Scenario:`.
`MODIFIED` requirements must include the complete updated requirement.
`REMOVED` requirements must include both a reason and migration note.
Capability names use kebab-case business noun phrases.
